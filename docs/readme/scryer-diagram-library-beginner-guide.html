先补基础：这套功能背后的 8 个技术概念

这里不是泛泛解释“什么是文件、什么是前端”。这 8 个概念都直接决定了设计文档为什么要写得那么细。 你先理解它们，后面看 Contract、Task、Verification 时就不会觉得是在堆文档。

1. 文件

`.scry` 是本功能的主要数据文件

Orca-Scryer 的模型数据主要保存在 `.scry` 文件里。它本质上是 JSON：用字段保存 nodes、edges、flows、diagrams 和 diagramRefs。

所以数据契约必须写清楚：新增字段是追加到现有 C4ModelData 上，而不是替换旧结构。

2. 数据结构

数据结构决定前端、MCP、测试怎么对齐

`Diagram.source` 是 Mermaid 源码，`DiagramRef.target` 是引用目标，`sourceRange` 是图源码位置。 这些字段一旦不统一，前端保存、MCP 工具、parser 校验、测试断言都会分叉。

3. 前端

前端负责用户状态，不直接当数据源

左侧 Diagram library、源码编辑器、SVG 预览、未保存 draft、target picker 都是前端状态。 文档要固定这些状态，是为了防止切换 C4/flow/diagram 时丢草稿。

4. Backend/API

后端/API 负责可信写入和工具调用

Orca 是 Electron 应用。Renderer 负责界面，Main process 才能安全读写本地文件。 IPC 和 MCP 工具必须有固定输入、输出和错误码，否则 Codex/Claude 外部调用会和 UI 写法不一致。

5. 持久化

持久化必须走真实 `.scry` 路径

只更新 React state 不算完成。必须通过 controller/model-store 写入 `.scry`，再 reload 证明数据还在。 所以测试文档反复强调真实文件读写。

6. 错误码

错误码让 UI、MCP、测试说同一种话

`controller.empty-source`、`renderer.invalid-source`、`cache.unauthorized-project` 这些不是装饰。 它们让失败原因可以被测试稳定断言，也让 UI 能显示友好文案。

7. 测试

测试要证明真实用户流程，不是证明空壳存在

这个功能跨前端、主进程、文件、MCP、缓存和 standalone。测试只看按钮渲染不够， 必须证明数据能保存、重新读取、外部工具可见、缓存不会越权。

8. 任务切片

任务切片是降低系统风险的方法

F1A 只做 schema/parser，S1A/S1B 只做源码保存和草稿保护，S2 才做渲染。 这样每个 PR 都能被真实验证，失败时也能定位是哪一层坏了。

从 7 种架构图角度看同一个功能

一个复杂功能不能只靠一张图讲清楚。C4 图回答“系统分几层”，时序图回答“调用顺序”，状态图回答“用户编辑时会发生什么”，数据模型图回答“文件里保存什么”。 设计文档把这些内容分开写，是为了让 Codex 实现时知道每一层的边界。

架构图视角 它主要看什么 为什么会影响设计文档
C4 / Container 图 Renderer 前端、Main process、model-store、MCP CLI、standalone scryer 分别属于什么边界。 所以 architecture doc 要规定文件归属，避免把主进程文件读写逻辑塞进 React 组件。
Component 图 `DiagramSourceDraftView`、`DiagramReviewView`、`diagram-renderer`、`parse-model`、`mcp-tools` 各自负责什么。 所以 implementation contract 要固定关键函数名和 props，避免写成一个巨大组件。
Sequence 图 用户点击保存后，前端、controller、IPC、model-store、`.scry` 的调用顺序。 所以 task 必须要求真实写入和 reload 证据，不能只证明内存状态改变。
State 图 draft、saved、dirty、external reload conflict、active diagram 这些状态怎么变化。 所以 S1B 要专门做草稿保护，否则用户切换页面时会丢未保存源码。
Data model / ER 图 `Diagram` 和 `DiagramRef` 怎么关联 C4 node、flow step、source file。 所以 contract 要写字段、删除策略、dangling ref、sourceRange 行号含义。
Security boundary 图 Renderer 传入的 projectPath、cacheKey、source pattern 是否能越权访问本机路径。 所以 S7A 要固定 cache 授权、大小限制、路径穿越防护，不能让 UI 任意读写文件。
AI prompt 流程图 Deep Build 从代码生成 diagram，Sync 更新 diagram，get_task 根据 diagram 辅助写代码。 所以 S6 必须接入现有 prompt 文件，并限制 AI 不要乱生成重复图。
为什么要从这么多图看？ 因为每种图只检查一种风险。C4 看“代码放哪层”，状态图看“会不会丢草稿”，时序图看“有没有真的写盘”， 数据模型图看“字段会不会乱”，安全边界图看“能不能越权读写文件”，prompt 流程图看“AI 会不会乱生成图”。
C4 / 分层图

决定代码应该放在哪一层

这个功能里，React 组件只负责界面；controller 负责把用户动作变成 mutation；Electron main process 才能安全读写本地文件； `.scry` 和 cache 是数据结果。C4/分层图把这些边界画清楚，后续 Codex 才不会把写文件逻辑直接放进按钮点击事件里。

状态图

决定用户切换页面时怎么保护数据

源码编辑不是“输入一个字就保存”。用户看到的是 draft，点 Save 后才变成 saved。 所以文档必须规定 dirty、saved、external reload conflict、activeDiagramId 等状态，否则用户切走 C4/flow 时可能丢内容。

时序图

决定“完成”是不是走了真实路线

时序图不是为了好看，而是为了检查调用顺序：前端保存、controller 校验、主进程写盘、reload 读取。 只要少一步，测试就可能变成“页面看起来变了，但文件没保存”。

安全边界图

决定哪些路径可以被读写

Renderer 传来的 `projectPath`、`cacheKey`、source pattern 都不能直接相信。 设计文档必须写授权函数、路径规则和错误码，是为了防止“一个图缓存功能”变成“任意读写本机文件”的漏洞。

前端、后端、数据层为什么都要写清楚

这个功能看起来只是“左边多一个图列表，右边显示 Mermaid”。但真实开发时，它同时跨过前端状态、主进程 API、本地文件、MCP 工具、缓存和测试证据。 full-stack 文档的作用，就是让每一层都知道自己负责什么、不负责什么。

前端层
负责：Diagram library 列表、源码编辑、未保存 draft、渲染结果展示、target picker、错误提示。
文档为什么要写：前端状态最容易让用户丢数据，所以要固定 `activeDiagramId`、`architectureMode`、dirty draft、external reload conflict。
Controller 层
负责：把用户动作变成受控 mutation，比如 create、rename、save、delete、request navigation。
文档为什么要写：组件不应该自己决定怎么写文件；所有用户导航都要经过 `requestArchitectureNavigation`，这样才能拦截未保存 draft。
后端/API 层
负责：Electron main process 的 IPC、MCP tools、CLI bridge、model-store 写入。
文档为什么要写：外部 Codex/Claude 通过 MCP 调用时看不到 React 组件，只能依赖工具 schema、错误码和返回结构。
数据层
负责：`.scry` 文件保存 nodes、edges、flows、diagrams、diagramRefs；`.scryer/cache/diagrams` 保存可重建缓存。
文档为什么要写：这里没有新增 SQLite 表。`.scry` 是长期数据，SVG/PNG/diagnostics 是可重建结果，二者不能混。
AI 层
负责：Deep Build、Sync、get_task prompt 告诉 Codex/Claude 什么时候创建、读取、更新 diagram。
文档为什么要写：AI 如果没有规则，会把普通 CRUD 也画成一堆图，导致 `.scry` 变臃肿。
测试层
负责：证明真实用户流程通过：真实 `.scry`、真实 reload、真实 MCP schema、真实 cache path。
文档为什么要写：mock 只能辅助，不能当完成证据。否则很容易出现“测试绿了，用户数据没保存”的假完成。
一句话总结： 前端负责“用户正在做什么”，后端/API 负责“可信地执行动作”，数据层负责“哪些内容长期保存”，测试负责“证明不是假完成”。 设计文档把这些层分开，是为了让 Codex 后续开发时少猜边界。

把这些层落到真实代码文件上

下面这张表是“读代码前的地图”。你不需要现在理解每个文件的实现，只要知道：设计文档为什么要把函数名、输入输出、错误码写死。

层 代表文件或模块 文档必须固定什么 不固定会怎样
前端 UI `ArchitecturePanel.tsx`、`ArchitectureModelTree.tsx`、`DiagramSourceDraftView.tsx`、未来的 `DiagramReviewView.tsx` 什么时候显示源码页、什么时候显示渲染页、按钮是否可见、dirty draft 如何提示。 容易出现半成品按钮，或者用户切换页面时丢失未保存源码。
前端 controller `useArchitectureModelController.ts`、`diagram-controller.ts` `createDiagram`、`updateDiagramSource`、`requestArchitectureNavigation` 的输入、输出、失败行为。 每个组件自己保存、自己导航，最后状态互相打架。
IPC/API `src/main/ipc/architecture.ts`、`src/preload/api-types.ts`、`src/preload/index.ts` renderer 调 main process 的请求和返回类型，cache 读写的成功/失败 union。 main process 改了，renderer 编译失败；或者 UI 以为成功，实际没写文件。
MCP 工具 `mcp-tools.ts`、`src/cli/scryer-mcp-server.ts` `set_diagrams`、`get_diagram`、`update_diagram_refs`、`delete_diagram` 的参数和返回结构。 Orca UI 能用，但外部 Codex/Claude 通过 MCP 看不到新能力。
数据 parser `model-types.ts`、`parse-model.ts`、`model-store-core.ts` 旧 `.scry` 如何升级到内存 v2，坏 ref 如何 warning，哪些字段写盘时保留。 打开旧文件就坏，或者保存时把已有 C4/flow 字段删掉。
渲染 adapter `diagram-kind.ts`、`diagram-renderer.ts`、`mermaid-render-queue.ts` Mermaid kind 检测、渲染函数名、安全清洗、`elementKey` 绑定规则。 不同地方用不同 Mermaid 判断；SVG 点击绑定不稳定；并发渲染随机失败。

为什么我要把开发文档设计成 PRD、Contract、Task、Test

这不是为了显得复杂，而是为了防止 Codex 在大功能里“猜着写”。对 AI 编码来说，文档不是作文， 而是防止写错代码、写空壳代码、写完无法验证的安全栏。

PRD

先固定“用户到底要什么”

例如：用户要求 diagram 和 C4 保存在同一个 `.scry` 里，但不能把 diagram 放进 C4 tree。 这属于产品目标，不是代码细节。

没有 PRD 的风险：Codex 可能做成另一个功能，比如把 UML 当成 C4 node。

Contract

再固定“代码之间怎么对接”

比如 `Diagram` 有哪些字段，`update_diagram_refs` 输入什么，错误用什么 code。 这些必须固定，否则前端、MCP、测试会写成不同版本。

没有 Contract 的风险：看起来都实现了，但字段名、错误格式、保存位置互相不兼容。

Task

然后固定“这次只做哪一小块”

例如 S1A 只做 Diagram library 和源码保存，不做 SVG 渲染。这样可以避免 Codex 顺手写半成品渲染壳。

没有 Task 的风险：一次改太多，坏了也不知道是哪一层坏。

Test

最后固定“怎么证明不是假完成”

比如必须真实写 `.scry`，reload 后还在；MCP 工具必须在 CLI bridge 里看得到。

没有 Test 的风险：按钮出现了，但文件没保存；mock 通过了，但真实用户用不了。

这样设计文档的目的

让 Codex 少猜，多按约定做

  • PRD 控制方向：别做错产品。
  • Contract 控制接口：别写成互相不兼容。
  • Task 控制范围：别一次写太多。
  • Test 控制证据：别假装完成。
不这样做会怎样

AI 很容易写出“看起来能用”的技术债

  • 只改 UI，不保存真实文件。
  • 只写一个空按钮，没有真实效果。
  • 只写 mock test，真实路径坏了不知道。
  • 每个模块自己猜字段，后面越改越乱。

每类文档其实是在挡一个具体风险

文档内容 它固定什么 对应的代码风险 在本功能里的例子
数据契约 字段名、类型、默认值、迁移规则、删除策略。 不同模块保存不同结构，或者打开旧模型时丢字段。 `C4ModelData` 只能追加 `diagrams` 和 `diagramRefs`，不能替换现有字段。
接口契约 IPC/MCP 的输入、输出、错误码、成功和失败返回形状。 UI、CLI、MCP 外部 agent 互相不兼容。 `delete_diagram` 删除 `.scry` 数据后，必须按规则清理 cache 或返回 warning。
前端状态契约 active view、draft、dirty、conflict、选择器、按钮状态。 用户切换 C4/flow/diagram 时丢草稿，或者按钮看起来可用但没有真实动作。 所有用户导航必须走 `requestArchitectureNavigation(...)`。
数据库/持久化契约 什么写进 `.scry`，什么写 cache，什么不进 SQLite。 模型不可移植、文件膨胀、缓存结果污染长期数据。 Diagram source 写 `.scry`，SVG/PNG 写 cache 或重新生成，不写 `orchestration.db`。
测试证据契约 哪些测试必须真实读写文件，哪些 mock 只能辅助。 出现“测试通过，但真实用户用不了”的假完成。 创建 diagram 后必须 reload `.scry` 证明仍存在。
任务切片 这次做什么、不做什么、依赖哪些前置任务。 一个 PR 横跨太多层，出了问题无法定位，也难 review。 S1 做 source-only 保存；S2 才做渲染；S7B 才做 copy/export。

一个好懂的比喻：一本设计书

想象 Orca 的 `.scry` 文件是一本项目设计书。C4、flow、diagram 不是互相替代，而是分工不同。

C4 tree

目录和章节结构

C4 告诉你系统有哪些大块，比如 Web App、Auth Service、Database。它负责整体结构。

Flow tree

办事流程清单

Flow 告诉你用户或系统怎么一步一步完成事情，比如登录、同步、导出。

Diagram library

附录里的图

Mermaid/UML 图放在附录里，用来解释细节，比如时序、状态、类关系、数据关系。

最重要的关系：引用，不是混在一起

我们不是把 diagram 当成 C4 node。正确做法是：C4 节点引用 diagram，flow 引用 diagram，代码文件也可以引用 diagram。

正确

diagram 独立保存，再用 diagramRefs 关联

  • C4 tree 保持简洁。
  • Flow tree 保持清楚。
  • Diagram library 专门放图。
  • 引用关系写在 `diagramRefs`。
错误

把 UML 图塞进 C4 node 或 flow

  • 树会越来越乱。
  • AI 容易误改 C4 结构。
  • 用户不知道哪些是系统结构，哪些只是补充图。
  • 后续同步和测试会变复杂。

哪些数据真正保存，哪些只是临时生成

这里有一个核心判断：能从 Mermaid 源码重新生成的东西，就不要当成真正数据保存。

写进 .scry

Source of truth

这是系统真正相信的数据。它应该长期保存。

  • C4 nodes 和 edges
  • flows
  • diagrams 的 Mermaid source
  • diagramRefs 引用关系
不写进 .scry

Derived cache

这是可以重新生成的结果。丢了也能从源码再做出来。

  • SVG
  • PNG
  • 缩略图
  • 渲染错误 diagnostics
  • sourceHash 和 rendererVersion

这里说的“数据库”到底是什么

Orca 项目里确实有 SQLite 依赖，但 Architecture 模型这条线的长期数据不是放在 SQLite 表里。 对这个功能来说，“Database/data contract”主要是在规定数据保存在哪里、谁能写、哪些东西不能写。

数据或结果 保存位置 为什么这样设计 设计文档要防什么
C4 nodes / edges `.scryer/<model>.scry` 它们本来就是 Architecture 模型的核心数据。 新增 diagram 时不能破坏原有 C4 字段。
flows / groups / sourceMap 同一个 `.scry` 文件 用户希望一个模型文件管理完整设计，不拆成很多散文件。 parser 和 serializer 不能在升级 schema 时丢旧字段。
Diagram.source 同一个 `.scry` 文件的 `diagrams` Mermaid/UML 源码是长期设计意图，必须跟模型一起移动和提交。 不能只存在前端内存里，也不能偷偷写进全局数据库。
DiagramRef 同一个 `.scry` 文件的 `diagramRefs` 引用关系是设计的一部分，比如“这个 C4 node 由哪张图解释”。 删除 node、flow、diagram 时必须清理或报告坏引用。
SVG / PNG / thumbnail `.scryer/cache/diagrams/...` 它们能从 Mermaid source 重新生成，丢了也不丢设计意图。 不能写回 `.scry`，否则模型文件会膨胀且容易过期。
SQLite / orchestration.db 本功能不新增 diagram 表 diagram 正文要跟 `.scry` 模型走，不能变成只在本机数据库可见。 防止“换一台机器打开模型，图没了”。

一次保存到底发生了什么

你可以把保存理解成一条固定路线。只改前端内存不算完成，必须真的写进 `.scry`，再重新读取验证。

1

用户编辑

在 DiagramSourceDraftView 或 DiagramReviewView 里改 Mermaid source。

2

Controller 接管

点击 Save 后，调用 `updateDiagramSource`，不是组件自己写文件。

3

IPC 传给主进程

前端通过 `architecture:*` IPC 让 main process 保存。

4

写入 .scry

model-store 把 diagrams 和 diagramRefs 写进真实文件。

5

Reload 验证

重新读取文件，确认数据还在。这样才算完成。

两个容易混的词：draft 和 saved

draft

草稿

用户正在编辑，但还没保存。输入时不会立刻写 `.scry`。

如果这时切走页面，必须问用户：保存、丢弃，还是取消。

saved

已保存

已经写进 `.scry`。重载模型后仍然存在。

cache、导出、MCP 同步都应该以已保存的 source 为准。

开发任务地图

这个功能不能一口气写完。每个任务只完成一段真实用户流程，并且必须有真实测试。

F1A
数据地基

.scry 认识 diagrams 和 diagramRefs。

S1A
创建和保存

左侧出现 Diagram library，源码能保存重载。

S1B
防止丢草稿

未保存切走时弹出保存、丢弃、取消。

F1B
渲染能力

Mermaid source 能变成安全 SVG。

S2
审查页面

同时显示源码、SVG 和错误信息。

S3
引用图

C4、flow、source 能引用已有 diagram。

红框里的三个模块，用白话再说一次

S3A

新建再关联

你正在看 C4 节点，想给它挂一张图，但图还不存在。S3A 允许你从这个节点旁边直接新建图，保存后自动回到这个节点，把图挂上。

它保护的是“我刚才要给谁加图”这个上下文。

S4

图内定位

这不是浏览器返回。它的意思是：UML/Mermaid 图里的某个框或箭头，可以绑定到 C4、flow 或源码位置。

如果一个元素只绑定一个目标，点击就直接打开；如果绑定多个目标，必须弹出选择列表，不能替用户猜。

S6

AI prompt 规则

Orca-Scryer 已经有 Deep Build、Sync、get_task 这些 AI prompt。get_task 是把 C4/flow 里的一个实现任务交给 Codex/Claude 的流程。

S6 不是另写一份散落的 Markdown，而是把 diagram 规则接进这些现有 prompt 文件。

目标是：代码能生成必要图；代码变更能同步图；实现代码时能读取相关图；但 AI 不能随便生成一堆重复图。

S6 不是一句提示词，而是三条 AI 路线

你可以把 AI prompt 理解成“交给 Codex/Claude 的施工说明”。S6 要做的是把 diagram 规则写进现有施工说明里， 并且保证三条路线用同一套规则，不要各写各的。

AI 路线 什么时候用 diagram 规则要写什么 为什么不能写得太宽
Deep Build 根据代码生成或补全 C4 model、flow tree。 如果代码里有复杂状态、调用顺序、类关系，才生成必要 Mermaid/UML 图；优先更新已有图。 如果写成“复杂就必须画图”，AI 会给每个小函数都画图，`.scry` 很快变臃肿。
Sync 代码变了，需要同步 C4、flow 和 diagram。 如果代码影响已有 diagram，优先更新那张图；不要重复创建表达同一件事的新图。 否则一次同步后会出现多张内容相近的图，用户不知道哪张是真的。
get_task / TASK_INSTRUCTIONS 从 C4/flow 里拿一个实现任务交给 Codex 写代码。 如果任务关联 diagram，prompt 先给 compact summary；需要完整源码时再调用 `get_diagram`。 直接把所有 diagram source 塞进 prompt，会让上下文变长，AI 更容易跑偏。
为什么设计文档要规定 prompt 文件归属？ 因为 prompt 规则如果散落在 `prompts.ts`、`rules.ts`、MCP instructions 里，后续很容易有一处更新、一处忘记更新。 所以正式文档要求共享函数放在 `prompt-diagram-instructions.ts`，其他入口只引用同一套输出。

正式文档为什么看起来那么难

PRD

回答“用户要什么”

比如：diagram 必须保存在同一个 `.scry`，不能塞进 C4 tree。

Contract

回答“代码必须怎么对接”

比如：函数输入输出、错误码、IPC、MCP、数据字段。

Task

回答“这次只做哪一小段”

比如：S1A 只做 source-only 保存，不做 SVG 渲染。

Test

回答“怎么证明真的完成”

比如：必须读写真实 `.scry`，不能只用 mock。

你后续看 Codex 输出时，只要会做 6 个判断

判断 1：是不是改对地方

C4 节点仍在 `nodes`，diagram 应该在 `diagrams`，引用关系在 `diagramRefs`。

判断 2：有没有真的保存

只改 React state 不够。必须写进真实 `.scry`，并 reload 后还能看到。

判断 3：有没有乱写缓存

SVG、PNG、diagnostics 不应该写进 `.scry`。

判断 4：有没有跳过任务顺序

没有 F1A，就不该做 S1A。没有 S2，就不该假装完整审查页完成。

判断 5：有没有保护草稿

未保存源码切走时，必须让用户选择保存、丢弃或取消。

判断 6：测试是不是走真实路径

mock 可以辅助，但完成证据必须包含真实 `.scry`、真实 MCP 或真实 cache 路径。

常见疑问

为什么不把 UML 直接变成 C4 node？

C4 node 表示系统结构，UML/Mermaid 图表示补充细节。混在一起后，树会变乱，AI 也更容易误改模型结构。

为什么 S1 只做源码，不做渲染？

因为先要保证 `.scry` 数据能正确保存。数据地基稳定后，再做 Mermaid 渲染，问题更容易定位。

为什么要这么多测试？

这个功能同时碰到 UI、文件保存、MCP、缓存和 standalone 兼容。只测一个组件出现了，不能证明用户真实使用时不会丢数据。

我需要先学完整 Web 开发吗？

不需要。先理解 `.scry`、Diagram、DiagramRef、保存路径、任务顺序。等做到具体任务时，再补对应知识。

阅读建议： 第一次只看“比喻”“数据”“任务地图”。等准备看 F1A 或 S1A 代码时，再回来看“保存流程”和“6 个判断”。 正式编码仍以仓库里的 contract、task、verification 文档为准。
